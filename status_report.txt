STATUS REPORT - DECAL RENDERING & ALPHA PIPELINE
=================================================
CURRENT STATE OF CODE:
1. `q3map/decals.c`:
   - Decal geometry projection is using bezier patch inflation properly.
   - The `target_position` distance logic is currently REVERTED to its original state where `distance = VectorLength(projNormal)`. This calculates the distance based exactly on where the target_position is placed.
   - The alpha interpolation formula is REVERTED to the standard `d2 / (d + d2)` formula, but currently has a hardcoded `alpha = 255.0f` override directly beneath it for testing purposes to isolate the invisibility bug.
   - The `hasVertexColor` flag is correctly set to `1` if `q3map_vertexcolor` is present, or `-1` if it is not.

2. `light/lightdata.c`:
   - `DownConvertDrawVerts` has been FIXED so that it only overwrites the 8-bit vertex colors (`drawVerts`) from the high-precision radiosity buffer (`internalDrawVerts`) IF the surface actually received vertex lighting (`ds->lightmapNum[0] < 0`).
   - This prevents `makelight` from blindly destroying the vertex colors generated by `makebsp` (which caused the black silhouette bug by replacing `255, 255, 255` with `0, 0, 0` on lightmapped decals).

THE TWO PROBLEMS WE EXPERIENCED & THEIR THEORIES:
A. The "Black Silhouette" Problem:
   - What happened: The decal shape was visible, but completely black, with the texture's alpha mask working correctly to outline it.
   - The cause: `makelight` was overwriting the `makebsp` vertex RGB (`255, 255, 255`) with `0, 0, 0` because it skips lighting calculations for lightmapped surfaces. Because the decal's shader uses `rgbGen vertex`, the engine multiplied the texture by `0, 0, 0` (turning it pitch black). Since the vertex alpha was left at 255, the mask still showed up.
   - The fix: `makelight` down-conversion fix (already implemented).

B. The "Missing Completely" Problem:
   - What happened: The decal completely disappeared from the map.
   - The user's theory: `alphaGen` in the engine is acting when it shouldn't be, masking 100% of the decal because of some property it has, likely related to how Q3 handles `rgbGen vertex` when no explicit `alphaGen` is defined.
   - My theory: The `target_position` distance logic placed the back clipping plane of the projector exactly on the wall (`d2 = 0`). Because the alpha interpolates from 255 (front) to 0 (back), this made the vertex alpha perfectly `0.0f` on the wall. When `makelight` was forcing alpha to 255 globally, this bug was hidden. When we stopped forcing it, the `0.0f` took effect, turning the decal 100% transparent. (Also, setting `distance` to a hardcoded 64 without extending the vector made the volume fall short of the wall entirely, clipping the decal out of existence).

WHAT WE NEED FOR TOMORROW:
1. We need to verify the result of the `alpha = 255.0f` hardcode test. If the decal returns as a black silhouette (or properly textured with the `makelight` fix), the invisibility was purely caused by the `0.0f` alpha calculation. If it remains missing, the user is correct and the engine is filtering it out based on a shader property.
2. We need to finalize the projector `distance` calculation. Using the exact `target_position` distance will guarantee `alpha = 0` at the wall under the standard interpolation formula. We either need to extend the projector depth past the target, ignore the target's distance entirely (only use it for direction), or implement an explicit `distance` key override.
3. We need to remove the hardcoded `alpha = 255.0f` override in `decals.c` and restore a safe alpha fading mechanism that doesn't punish decals that land precisely on their target.
4. If the decal shader requires `rgbGen vertex` to tint decals via entities, we must ensure the engine handles the implied `alphaGen` correctly without destroying the texture's alphamap.
