# Lightgrid Downtone Curve

### The Curve
To prevent incredibly bright point lights from creating harsh, unnatural ambient blowouts in the lightgrid, a smooth exponential roll-off curve is used. 

The formula is:
new_luma = maxAmbientAllowed * (1.0f - expf(-lumAmb / maxAmbientAllowed));

Instead of hitting a hard "brick wall" clamp, this curve allows light values to scale linearly at lower intensities, and then gracefully round off as they approach the maxAmbientAllowed ceiling.

### Application Scope
This ramp is strictly intended to be applied individually to each light as it contributes its energy to the lightgrid's ambient component. It is mathematically designed to govern how single light entities behave, and is not intended to be used on the final mixed/accumulated sum in the post-processing filters.

### The Problem with Surface Lights (Multiple Emitters)
When applying this individual ramp, surface area lights present a unique mathematical problem. 

A surface light is not a single entity; the compiler subdivides it into hundreds or thousands of tiny individual emitters (patches). 
1. The Crushing Problem: If the maximum allowed value is scaled down for each tiny emitter, the curve engages prematurely on every single tiny patch. As a result, the individual pieces are severely crushed before they can combine, resulting in surface lights that are far too dim compared to point lights.
2. The Blowout Problem: Conversely, if each tiny emitter calculates the curve against the global max, their individual values are so small that they fall into the linear part of the curve. The curve essentially ignores them, allowing them to stack linearly until their accumulated total blows way past the global ambient limit.

Because the ramp must be applied individually to lights, surface lights require special scaling logic to prevent their subdivided nature from either circumventing the ceiling or prematurely crushing the output.

### The Solution: The Family Count
To solve the surface light problem, the compiler now tracks the number of subdivided patches that make up the original parent light (the `familyCount`).

When processing an individual tiny patch's contribution to a grid cell:
1. **Simulate Full Brilliance:** The patch's tiny luminance is artificially inflated by multiplying it by the `familyCount`, predicting what the full, undivided surface light would equal at that distance.
2. **Apply the Curve:** The curve is evaluated against this simulated, massive luminance.
3. **Deflate Back to Share:** The squashed result is then divided back down by the `familyCount`, returning it to the exact mathematical fraction this individual patch is responsible for.

This perfectly fixes both the Crushing Problem and the Blowout Problem, ensuring surface lights are evaluated by the exponential curve with the exact same weight as single point lights.

### Current Status
**Temporarily Disabled:** The curve evaluation block in `TraceGrid` (`light_direct.c`) is currently disabled (`if (0 && ...)`) for debugging purposes. 
The presence of a strict, hard ceiling (`LIGHTGRID_AMBIENT_MAX_LUMA`) applied *after* the curve made the curve's smooth roll-off mostly invisible, as any intensely bright values were brutally chopped off by the hard clamp regardless. The curve is bypassed while debugging ambient bleed features.
